Methodology and caveats

What is measured

  • Every app implements the same storefront from benchmarks/SPEC.md and passes verify, which compares visible text, element counts and JSON with the reference app.
  • Apps run one at a time on a free port, in their own process group, with the same environment. Each scenario gets a warmup, then the measured runs. With several runs the median by throughput is shown.
  • Load comes from oha over HTTP/1.1 keep-alive connections. Every request carries a cart_count cookie. The detail scenarios rotate over every product id; the cart scenario rotates over valid request bodies.
  • Any non-2xx/3xx response, connection error or timeout marks the whole measurement invalid. Invalid measurements are listed but never drawn as bars, so an app that answers errors quickly cannot look fast.
  • Memory is sampled from the app's whole process tree, so forked workers count. On Linux it is the proportional set size, which splits shared pages between processes; on macOS it is the resident set size, which counts shared pages once per process and so overstates multi-process servers.
  • CPU time is the user plus system time of the whole process tree during the measured run. Requests per CPU-second divides successful requests by it.
  • With a thread limit (BENCH_THREADS=N), apps are pinned to N CPUs on Linux. On every platform a measurement whose process tree kept materially more than N cores busy is flagged as exceeding the thread limit and is not compared.
  • With compression on, requests send the Accept-Encoding of a current browser, so these runs compare each framework's default compression algorithm and level. The negotiated Content-Encoding is recorded per scenario and shown next to each figure.
  • The latency phase, when enabled, is open-loop: requests are sent at a fixed rate and latency is measured from when each request was scheduled, which corrects for coordinated omission. In relative mode the rate is a fraction of each app's own measured throughput; in fixed mode it is the same for every app.

What is not measured

  • No database: the data layer is in memory by design, so the numbers show the cost of routing, rendering and serialization, not of I/O. Real applications usually spend much of their time elsewhere.
  • No TLS, no HTTP/2, no reverse proxy, no network latency. Compression is only on when the configuration says so.
  • Browser-side cost: hydration time, time to interactive and memory in the browser are not measured. The payload section shows bytes only.

Caveats

  • The frameworks differ in kind. Next.js, Leptos and Dioxus render on the server and then hydrate a client runtime: the server does extra work to serialize state and emit hydration markers, and the browser downloads a JavaScript or WebAssembly bundle. Leptos islands hydrates only the interactive parts and ships less. Topcoat, Axum with Maud, Rails, Django, Phoenix, ASP.NET Core and Go with templ render on the server and ship small or no client runtimes. Server throughput alone does not capture this trade-off; read it together with the client payload.
  • The load generator shares the machine with the server and competes with it for CPU. Very fast servers are partly limited by the load generator, so differences at the top end are compressed.
  • Results depend on the machine, the operating system and its scheduler, thermal state and background load. Compare numbers from the same run only.
  • Short profiles (such as quick) are for smoke testing. JIT-compiled runtimes need longer warmups than they provide.
