Use localization to show text in each user's language, whether it ends up in a page, an email or a push notification. Enable the `l10n` feature of `topcoat`, choose a locale, and store it in the context.

Enable `l10n-fluent` to use [Fluent](https://projectfluent.org/) files, as shown in the [Fluent section](#fluent).

# Choosing the locale

A [`Locale`] is a language with an optional script and region, such as `en`, `zh-Hant` for Chinese in the traditional script, or `de-CH` for German as used in Switzerland. Write a fixed locale with [`locale!`](macro@locale), which fails to compile when the locale is invalid, or parse a string with `"de-CH".parse()`.

Your app adds the locale to the context with [`Cx::with`](crate::context::Cx::with). Everything that uses the context can then read it with [`locale`](fn@locale).

For a page, set the request's locale in a [`#[layer]`](crate::router::layer) so it is available before the page renders. A context created inside a layout does not reach the page. Also set the `lang` and `dir` attributes on `<html>` to match the locale, as in the examples below.

## From the browser's languages

[`accept_language`] reads the browser's preferred languages. Pass them and your supported locales to [`negotiate`] to find a match:

```rust,no_run
use topcoat::{
    Result,
    context::Cx,
    l10n::{Locale, accept_language, locale, negotiate},
    router::{Body, Next, layer, module_router, page, response::Response},
    view::{View, view},
};

const LOCALES: [Locale; 2] = [locale!("en"), locale!("de")];

#[tokio::main]
async fn main() {
    topcoat::start(module_router!().build()).await.unwrap();
}

#[layer]
async fn layer(cx: &Cx, body: Body, next: Next<'_>) -> Result<Response> {
    let locale = negotiate(accept_language(cx), &LOCALES)
        .cloned()
        .unwrap_or(locale!("en"));
    next.run(&cx.with(locale), body).await
}

#[page]
async fn home(cx: &Cx) -> Result<impl View> {
    Ok(view! {
        <!DOCTYPE html>
        <html lang=(locale(cx).id()) dir=(locale(cx).id().direction())>
            <body>
                <p>"The page is in " (locale(cx))</p>
            </body>
        </html>
    })
}
```

## From the URL

Many apps put the locale at the start of the URL, as in `/en/about` or `/de/about`, so every language has its own links. Put the pages in a module with a [`module_param!`](crate::router::module_param) of type [`Locale`], and set the locale in that module's layer:

```rust,no_run
use topcoat::{
    Result,
    context::Cx,
    l10n::{Locale, locale},
    router::{
        Body, Next, error::not_found, layer, module_param, module_router, page, path_param,
        response::Response,
    },
    view::{View, view},
};

const LOCALES: [Locale; 2] = [locale!("en"), locale!("de")];

#[tokio::main]
async fn main() {
    topcoat::start(module_router!().build()).await.unwrap();
}

mod localized {
    use super::*;

    // Matches the first part of the URL, as in /en or /de.
    module_param!(pub path_locale: Locale, error = not_found);

    #[layer]
    async fn layer(cx: &Cx, body: Body, next: Next<'_>) -> Result<Response> {
        let path_locale = path_param::<PathLocale>(cx)?;
        // Any locale can be typed into the URL, so reject the ones your app lacks.
        if !LOCALES.contains(path_locale) {
            return Err(not_found().into());
        }
        next.run(&cx.with(path_locale.clone()), body).await
    }

    #[page]
    async fn home(cx: &Cx) -> Result<impl View> {
        Ok(view! {
            <!DOCTYPE html>
            <html lang=(locale(cx).id()) dir=(locale(cx).id().direction())>
                <body>
                    <p>"The page is in " (locale(cx))</p>
                </body>
            </html>
        })
    }
}
```

Visitors who open `/` do not have a locale in the URL yet. Add a page there that picks one [from the browser's languages](#from-the-browsers-languages) and redirects to it. See `examples/l10n` in the repository for a complete app.

## Outside a page

Text that is not part of a page, such as an email or a push notification, should use the locale of the person who receives it, which is not always the locale of the current request. Store it with their account, for example, and add it to a context with `cx.with(locale)` or `Cx::default().with(locale)`.

# Fluent

[Fluent](https://projectfluent.org/) is a localization system made by Mozilla. A Fluent file holds the messages of one language. A message can use variables and choose its words by number or gender, so translators can write natural sentences without changing your code.

With `l10n-fluent`, store each locale's messages in a file named after that locale. For example, put English messages in `src/l10n/en.ftl`:

```fluent
title = Welcome
greeting = Hello, { $name }!
search = Search
    .placeholder = Type to search
```

Put the matching German messages in `src/l10n/de.ftl`:

```fluent
title = Willkommen
greeting = Hallo, { $name }!
search = Suche
    .placeholder = Suchbegriff eingeben
```

Call `messages!("./l10n/{locale}.ftl")` in `src/main.rs` to load these files. The macro creates `t!` for translating messages and `t::locales()` for listing the available locales. You can pass that list to [`negotiate`].

## Paths

The path passed to `messages!` contains `{locale}` where the locale name belongs. It decides where the path starts:

- `./` and `../` are relative to the source file that calls `messages!`, so `"./l10n/{locale}.ftl"` in `src/main.rs` matches `src/l10n/en.ftl`.
- `{mod}` is the directory of the current module's child modules, so `"{mod}/l10n/{locale}.ftl"` in `src/admin.rs` matches `src/admin/l10n/en.ftl`.
- `/` starts an absolute path.
- Any other path is relative to the crate's `Cargo.toml`, so `"l10n/{locale}.ftl"` matches `l10n/en.ftl` next to it.

To split a locale's messages into several files, use the wildcards `*`, which matches any characters within one file or directory name, and `**`, which matches any number of directories. `"./l10n/{locale}/**/*.ftl"` matches `src/l10n/en/home.ftl` and `src/l10n/en/forms/login.ftl`, and all files of a locale are loaded together. See [`messages!`](fluent::messages) for the exact rules.

## Translating

Pass a message ID to `t!`, then any arguments the message needs. Add `.name` to select a message attribute:

```rust
# topcoat::l10n::fluent::messages!("l10n/{locale}.ftl");
let name = "Ada";
let title = t!(title);
let greeting = t!(greeting, name = "Ada");
// Short for `name = name`.
let greeting = t!(greeting, name);
let placeholder = t!(search.placeholder);
```

Fluent IDs often contain hyphens, such as `search-field`. rustfmt reads a hyphen as a minus sign and formats `t!(search-field)` as `t!(search - field)`. The macro still finds the right message, but the code is harder to read. To keep the hyphens together, write the key and the argument names as string literals, as in `t!("search-field.placeholder")` and `t!(greeting, "user-name" = name)`. You can also use snake case IDs such as `search_field` in your Fluent files.

In a view, the translation uses the locale in the current context. To get the text directly, call [`resolve`](Translation::resolve) with a context or [`resolve_in`](Translation::resolve_in) with a locale:

```rust
# use topcoat::{context::Cx, l10n::locale};
# topcoat::l10n::fluent::messages!("l10n/{locale}.ftl");
let cx = &Cx::default().with(locale!("de"));
assert_eq!(t!(title).resolve(cx), "Willkommen");
assert_eq!(t!(title).resolve_in(&locale!("en")), "Welcome");
```

## Several sets of messages

Call `messages!` in more than one module to give a page or a feature its own messages. Each call creates a `t!` in its module that only translates the messages of its own files, so different modules can use the same message IDs. Keeping a feature's files next to its code, with a path such as `"{mod}/l10n/{locale}.ftl"`, also lets you move or delete the feature together with its translations.

```rust
# use topcoat::{context::Cx, l10n::locale};
topcoat::l10n::fluent::messages!("l10n/{locale}.ftl");

mod admin {
    topcoat::l10n::fluent::messages!(pub(crate) "l10n/admin/{locale}.ftl");
}

let cx = &Cx::default().with(locale!("de"));
assert_eq!(t!(title).resolve(cx), "Willkommen");
assert_eq!(admin::t!(title).resolve(cx), "Verwaltung");
```

Import a `t!` into other modules like any other item, as in `use crate::admin::t;`. A module can only call `messages!` once, and it cannot import another `t` next to its own.

Each set of messages has its own locales, which `t::locales()` of its module returns. When a set lacks the request's locale, it uses a fallback locale with files, such as `de` for `de-CH`.

## Regional locales

Regional files can contain just the messages they need to override. If you have both `de.ftl` and `de-CH.ftl`, `de-CH` uses messages from `de` when they are absent from its own file. This fallback stays within the same language.

## Missing messages

When no message is available for the locale, Topcoat displays its key and arguments, such as `greeting(name = "Ada")`. It does not switch to another language. This lets you build pages while translations are still missing.

## Checking messages

Run this command to check your app's translations:

```sh
topcoat l10n check
```

For each locale, the command shows how many keys used by `t!` are available. It reports an error when:

- a locale is missing a message or attribute used by `t!`,
- a message needs a variable that its `t!` call does not supply,
- a Fluent message refers to a message, term or attribute that is missing.

The command also warns about unused messages and arguments. It checks the `t!` calls kept in the compiled binary, so calls removed as unused by the compiler do not count. Errors produce a nonzero exit status, which you can use to fail a CI check.

`topcoat dev` checks translations after each build and warns when it finds problems.

Cargo tracks changes to existing `.ftl` files, but does not notice newly added ones. A plain `cargo build` includes a new file only after another file in the crate changes. `topcoat dev` triggers a rebuild when you add a file. `topcoat l10n check` also forces the message files to be loaded again before checking them.
